# Архитектура

Точка входа для человека. Агентам — `AGENTS.md`. Что система делает — `specs/use-cases.md`.

## Что это

Event-driven control plane над жизненным циклом PR. Переписывание GC-автоматики из Nucex в
отдельный переиспользуемый продукт. Однопользовательский: один инстанс обслуживает одного
владельца и его репозитории.

Система собирается из **исполняемых спек**: поведение домена описано таблицами
given/when/then, реализация пишется под них.

## Части

Один бинарник, внутри — пакеты с разной ответственностью.

| Пакет | Ответственность |
|---|---|
| `internal/domain` | Чистое ядро: словарь фактов, `Decide`, `Evolve`. Не знает ни про SQLite, ни про GitHub, ни про HTTP. |
| `internal/github` | Формат GitHub: разбор вебхуков в команды домена, разбор ответов API. |
| `internal/store` | Журнал, очередь задач и настройки в SQLite. |
| `internal/web` | HTTP: страницы админки, формы, фрагменты htmx, путь вебхука. |
| `internal/agent` | Запуск Codex, рабочие копии, `git`, создание PR. |
| `internal/app` | Сборка: планировщик, исполнитель задач, порты, старт и остановка. |
| `cmd/gc` | `main`: читает env, собирает `internal/app`, запускает. |

```
GitHub ──вебхуки──▶ HTTP ──▶ журнал ──задача──▶ исполнитель ──▶ Codex ──▶ API модели
                     ▲          │  ▲                  │
                  админка ──────┘  └────результат─────┘
```

## Решения и почему

### Go и htmx выбраны ради петли обратной связи

Прошлый стек проверял домен за секунды, но полная петля упиралась в эмуляцию бэкенда и в DOM.
Здесь тесты домена — обычные табличные тесты без окружения, а сценарий целиком проверяется
через `net/http/httptest` и HTML-ответ: страница отдаётся сервером, поэтому проверять её можно
разбором тела ответа, без браузера.

Плата за это — ручная работа там, где раньше был фреймворк: SQL пишем сами, HTML собираем
сами, реактивности из коробки нет. Мы на это идём сознательно: объём продукта невелик, а
скорость петли важнее.

### Журнал append-only — единственный источник правды

Всё, что произошло, лежит одной последовательностью фактов. Записи не изменяются и не
удаляются. Текущее доменное состояние — не отдельная таблица, а свёртка журнала.

Отсюда два следствия. Первое: секреты в журнал не попадают никогда — переписать его нечем,
и утёкший туда ключ останется навсегда. Секреты приходят из окружения и не хранятся в базе.

Второе: append-only лог **сам по себе является наблюдаемостью**. Метрики выводимы из него
задним числом, обратное — нет. Поэтому на старте мы не поднимаем ни Grafana, ни метрики вовсе.

### SQLite и один процесс

Нагрузка — десятки событий в час и единицы задач. Для неё сетевая база и отдельный воркер были
бы ценой без выгоды. Один файл базы даёт транзакцию, которая одновременно пишет факты и ставит
задачу, — журнал и очередь не расходятся без распределённых ухищрений.

Прошлый стек держал отдельный воркер вынужденно: у функции бэкенда было 10 минут, 512 МБ, не
было файловой системы и нельзя было порождать процессы. Обычный процесс этих ограничений не
имеет: клонировать репозиторий и запустить Codex он может сам. Вместе с воркером уходят
протокол аренды между процессами, отдельный worker credential и выдача токенов наружу.

Условие обратимости: очередь читается через интерфейс, а исполнение задачи не лезет в базу
напрямую. Пока это так, вынести исполнителя в отдельный процесс можно без переписывания домена.
Цена решения честная: горизонтально инстанс не масштабируется, и это осознанно.

### Дедупликация по webhook delivery id

GitHub может доставить один и тот же вебхук дважды. Каждая доставка несёт уникальный
идентификатор (`X-GitHub-Delivery`). Мы его запоминаем и повторную доставку отбрасываем на
приёме.

HTTP boundary проверяет `X-Hub-Signature-256` **до** dedupe и разбора. Невалидная подпись не
пишет журнал и не вызывает parser.

Это первая линия. Вторая — форма самого домена: `Decide` выпускает `PrStateChanged` только
если снимок отличается от известного. `updatedAt` не даёт поздней доставке старого состояния
откатить новое. Даже если дубль просочится, факта не появится.

Одна check delivery даёт 0..N команд по уникальным PR associations. Required-check inventory
в вебхуке не приходит и там не вычисляется.

### PAT вместо GitHub App

Прошлая версия несла установку App, OAuth с PKCE, сверку установки и чеканку installation-токенов.
Для одного владельца это было бы сложностью без выгоды: App даёт мультитенантность и выбор
репозиториев на стороне GitHub, а нам нужен доступ к своим репозиториям.

Поэтому доступ даёт PAT из окружения, а список репозиториев ведётся в админке. Токен один на
инстанс, в базу и в журнал не попадает. Ограничение записанное: срок жизни и отзыв токена —
ответственность оператора, система об истечении узнает только по ошибке от GitHub.

### Полнота evidence принадлежит свипу

Webhook observations полезны для живого экрана, но не доказывают, что отсутствующая required
identity действительно отсутствует. Перед решением каждый PR получает полный
`RequiredChecksObserved` или `LookupIncomplete` с тем же `sweepId`. Partial pagination
порождает только failure. Старое evidence не переиспользуется следующим свипом.

Каждая попытка lookup сначала читает свежий PR и только затем защиту ветки и runs его
текущего head. Это же обновляет nullable `mergeable`: одноразовая reconciliation после
`PrCreated` восстанавливает ранние вебхуки, но не заменяет refresh перед каждым свипом.

Адаптер передаёт полный inventory и все attempts. Последнюю попытку по `createdAt`, затем `id`,
а также passing conclusions вычисляет домен.

### Создание PR всегда запускает reconciliation

Webhook check run может прийти до создания PR и без associations. Поэтому `PrCreated`
отображается в `ReconcilePr`: адаптер читает текущий PR и все runs его head, после чего
отправляет обычные `ObservePr` и `ObserveCheckRun`. Отдельной параллельной модели фактов для
reconciliation нет.

### Время попадает в домен только тиком

Домен не читает часы. Текущее время приезжает командой `TickProduction` или `TickSweep`.
Иначе спеки становятся невоспроизводимыми: таблица, зависящая от текущего времени, зелёная
сегодня и красная завтра.

Долговечных таймеров нет: расписание держит планировщик в процессе. Условие обратимости этого
решения — **`Decide` не возвращает эффект «разбуди меня в момент T»**. Как только такой
эффект появится, знание о планировании времени протечёт в домен, и вернуться будет дорого.

Планировщик не принимает аргументов репозитория: часовой wake-up перечисляет подключённые
репозитории и шлёт due-тик по каждому, шестичасовой шлёт свип по каждому.

### Шов между HTTP и доменом — заметка на потом

Декларативных констант недостаточно: путь может быть смонтирован, но не писать журнал.
Поэтому сценарные тесты поднимают настоящий HTTP-сервер через `httptest`, ходят по нему
запросами и читают HTML. Подменяются только внешние порты: GitHub, Codex, файловая система и
часы. Шесть строк проверяют handoff, не повторяя доменные матрицы.

Зелёные доменные таблицы при красных сценарных означают незавершённое приложение.

### Настройки и секреты

Настройки живут в SQLite и меняются формами админки; изменение пишется фактом. Секреты живут
только в окружении. Каждый due-тик несёт снимок настроек своей попытки, и задача не перечитывает
настройки перед исполнением.

Optional OpenAI Base URL нормализуется как абсолютный HTTP(S) URL без credentials, query и
fragment; пустое значение означает официальный endpoint.

## Стек

| Слой | Выбор |
|---|---|
| Язык, сборка, тесты | Go, стандартный `testing`, `go test` |
| HTTP | `net/http` из стандартной библиотеки |
| Шаблоны | `html/template` |
| Интерактивность | htmx, без сборки фронтенда |
| Хранилище | SQLite |
| Агент | Codex как подпроцесс |
| Деплой | один бинарник на VPS, Docker необязателен |

**Что рассматривали и отклонили:** веб-фреймворки поверх `net/http` (маршрутизатор стандартной
библиотеки закрывает наши нужды), ORM (SQL здесь проще схемы поверх него), React и любой сборщик
фронтенда (ради них и уходили), отдельный воркер и очередь-сервис (не нужны в одном процессе),
Postgres (нагрузка не требует, а цена — второй сервис), метрики и трейсинг (журнал даёт то же),
GitHub App (мультитенантность не нужна).

## Что переносится из Nucex, а что нет

**Переносится:** протокол сессии (`PROMPT.md`, заморозка, случайные фикстуры), порог admission,
идея исполняемых таблиц.

**Не переносится:** двухтокенная схема (её причина — PAT на руках у LLM-агента, здесь агент
GitHub не трогает); числа 160, 170, шестичасовой дедлайн дрейна и потолок раундов (это обход
лимита джобы GitHub Actions в 150 минут, а не правила домена); lifecycle fingerprint (артефакт
поллинга — при вебхуках перезапуск проверки приезжает событием сам); `baseSha` (уход базы
вперёд не обесценивает зелёный CI на текущем head).
