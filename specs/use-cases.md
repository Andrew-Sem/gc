# Юзкейсы

Шесть сценариев в двух группах. Два выполняет система сама, четыре — человек в админке.

## Система работает по двум правилам

1. **Раз в час** — если открытых PR меньше 12, завести один PR.
2. **Раз в 6 часов** — по каждому открытому PR: можно мержить — мержим; нельзя — пишем
   причину; старше 24 часов — закрываем.

**PR мы не чиним.** Упавший PR ждёт сутки — за это время человек может успеть поправить —
и закрывается. Единственная поблажка: один перезапуск CI перед закрытием, чтобы флейк не
убивал нормальную работу.

Порог объёма — единственный ограничитель производства. Порога возраста в admission нет
намеренно: он дублировал бы закрытие по возрасту и создавал бы окно простоя между «PR
достиг суток» и «свип его закрыл».

---

## 1. Завести новую работу

**Триггер:** тик раз в час.

**Admission проверяет:** открытых PR меньше 12.

Число открытых берётся из **нашего же журнала**: мы эти PR создавали и видим, когда они
закрываются. У GitHub его не спрашиваем. Побочный эффект приятный: если вебхук о закрытии
потеряется, счёт окажется завышен — система станет осторожнее, а не наглее.

**Если разрешено:** `AdmissionApproved`, воркер запускает Codex, тот заводит PR.
**Если нет:** `AdmissionDeclined` с числами. Отказ пишется всегда — иначе экран не ответит,
почему час прошёл впустую.

**Что агент ищет:** пока общий промпт, агент сам решает, что почистить. Промпт лежит в
настройках тенанта.

## 2. Довести PR до мержа

**Триггер:** тик раз в 6 часов.

**Merge-gate проверяет четыре условия:**

1. PR открыт и не в драфте
2. head тот же, на котором зеленел CI
3. обязательные проверки прошли
4. GitHub говорит `mergeable`

**Обязательными считаются проверки из защиты ветки GitHub**, не свой список в конфиге —
иначе два источника правды разъедутся. Если защита ветки не настроена и обязательных нет
вообще, не мержим.

**Если всё сошлось:** `MergeApproved`, эффект вызывает GitHub. Успех приедет наблюдением.
Провал — `MergeFailed`.
**Если нет:** `MergeDeclined` с причиной.
**Если PR старше 24 часов:** `CloseApproved`.

Фактическое закрытие произойдёт между 24 и 30 часами — точность ограничена шагом свипа.

## 3. Подключить репозиторий

GitHub App создаётся и ставится на репозитории **руками, на стороне GitHub**. В админку
вставляются App ID, installation ID и приватный ключ. После этого система запрашивает список
доступных установке репозиториев, человек отмечает нужные.

Долгоживущих токенов у GitHub App нет: из App ID и приватного ключа чеканится JWT на 10
минут, он меняется на installation-токен на час.

## 4. Настроить модель и ключ

Два способа входа: свой API-ключ или **подписка Codex** через device-code login. Второй
сделан именно для headless: система показывает ссылку и код, человек подтверждает в браузере
у себя.

Credentials пишутся в `$CODEX_HOME/auth.json`. Файл один на `CODEX_HOME`, поэтому
`CODEX_HOME` должен быть свой на каждого тенанта.

В журнал попадает только факт подключения, никогда сами токены — журнал вечный.

## 5. Настроить темп и пороги

Настройки живут на двух уровнях:

| Уровень | Что настраивается |
|---|---|
| Тенант | модель и ризонинг, ключ или подписка, промпт агента |
| Репозиторий | как часто заводим, максимум открытых, через сколько закрываем |

Изменения действуют **со следующего тика**, задним числом ничего не пересчитывается.
Понизил порог с 12 до 5, когда открыто 9 — новые не заводятся, пока не опустится до пяти,
но уже открытые никто не трогает.

Ролей нет: у тенанта один владелец.

## 6. Понять, почему PR висит

Ради этого сценария и заводится свой экран. Он показывает цепочку:

```
что известно  →  что решили  →  почему именно  →  что дальше
```

Вердикт **пересчитывается на лету** на текущем состоянии журнала, а не берётся последний
записанный на свипе. «Шесть часов назад было красное» бесполезно, если тест уже починили.
Цена: показанный вердикт — прогноз, а не факт.
