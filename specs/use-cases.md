# Юзкейсы

Шесть сценариев в двух группах. Два выполняет система сама, четыре — человек в админке.
Все четыре человеческих сценария выполняются через интерактивное browser application. Прямой
вызов backend functions не считается реализацией UI. Полный runtime contract описан в
`specs/runtime.md`.

## Система работает по двум правилам

1. **Каждый час wake-up** — для репозиториев, чей настроенный темп наступил: если открытых PR
   меньше лимита, завести один PR.
2. **Раз в 6 часов** — по каждому открытому PR: можно мержить — мержим; нельзя — пишем
   причину; старше настроенного возраста закрываем, по умолчанию через 24 часа.

**PR мы не чиним.** По умолчанию упавший PR ждёт сутки — за это время человек может успеть
поправить — и закрывается. Перезапусков CI не делаем: флейкнувший тест иногда съест
нормальную работу, но через час заведётся новый PR, а перезапуск завёл бы в систему счётчики
попыток.

Порог объёма — единственный ограничитель производства. Порога возраста в admission нет
намеренно: он дублировал бы закрытие по возрасту и создавал бы окно простоя между «PR
достиг суток» и «свип его закрыл».

---

## 1. Завести новую работу

**Триггер:** due-тик после часового wake-up. Темп задаётся целым числом часов. Сохранение
нового темпа начинает новый интервал; само сохранение решения не запускает.

**Admission проверяет:** открытых PR меньше лимита из снимка настроек этого тика. Тот же тик
несёт снимок tenant settings и boundary-настройки OpenAI Base URL для будущего запуска агента;
уже созданная задача не перечитывает из mutable storage модель, reasoning, prompt или Base URL
перед исполнением.

Число открытых берётся из **нашего же журнала**: мы эти PR создавали и видим, когда они
закрываются. У GitHub его не спрашиваем. Побочный эффект приятный: если вебхук о закрытии
потеряется, счёт окажется завышен — система станет осторожнее, а не наглее.

**Одобрение места не резервирует.** Слот занимает только реально созданный PR. Между
одобрением и появлением PR проходит время работы Codex, поэтому следующий тик может одобрить
ещё раз: тик в 13:00 одобрил, Codex работает 70 минут, тик в 14:00 одобряет снова. Открытых
станет 13 при пороге 12.

Это осознанно: 12 — показатель здоровья, а не жёсткий предел, а резервирование завело бы в
домен время жизни, которое домен сам закончить не может — упавший воркер держал бы слот вечно.
Защита от двух одновременных заходов по одному репозиторию живёт в воркере, не в домене.

**Если разрешено:** `AdmissionApproved`, воркер запускает Codex, тот заводит PR.
**Если нет:** `AdmissionDeclined` с числами. Отказ пишется всегда — иначе экран не ответит,
почему час прошёл впустую.

Если агент упал до создания PR, `AgentRunFinished` записывается с tenant/repo и без PR.

**Что агент ищет:** пока общий промпт, агент сам решает, что почистить. Промпт лежит в
настройках тенанта.

## 2. Довести PR до мержа

**Триггер:** тик раз в 6 часов.

Перед решением orchestration получает для каждого открытого PR один терминальный результат
текущего `sweepId`: либо полный evidence snapshot, либо `LookupIncomplete`.

Перед required-check lookup orchestration заново читает текущий PR. Если GitHub ещё считает
`mergeable` или head изменился, свежий снимок попадает в журнал, а checks запрашиваются для
head из этого ответа.

**Merge-gate проверяет четыре условия:**

1. PR открыт и не в драфте
2. head тот же, на котором зеленел CI
3. обязательные проверки прошли
4. GitHub говорит `mergeable`

**Обязательными считаются проверки из защиты ветки GitHub**, не свой список в конфиге.
Required identity — `context + appId`. Evidence содержит полный required inventory и все
check-run attempts текущего head. Для каждой identity нормативна последняя попытка по
`createdAt`, затем `id`. `success`, `neutral`, `skipped` проходят; остальные completed
conclusions отказывают; незавершённые statuses и отсутствующая попытка ждут.

Если защита ветки не настроена и обязательных нет, не мержим. Partial pagination никогда не
считается полным снимком. `LookupIncomplete` блокирует мерж и закрытие только текущего свипа;
следующий свип получает собственный evidence заново. Старый снимок новый свип не заменяет.

**Если всё сошлось:** `MergeApproved`, эффект вызывает GitHub. Успех приедет наблюдением.
Провал — `MergeFailed`.
**Если нет:** `MergeDeclined` с причиной.
**Если PR достиг настроенного `closeAfterHours`:** `CloseApproved`. По умолчанию 24 часа.

Фактическое закрытие произойдёт между `closeAfterHours` и `closeAfterHours + 6` часами —
точность ограничена шагом свипа.

## 3. Подключить репозиторий

На один deployment оператор заранее регистрирует **один общий GitHub App**. Владелец тенанта не
создаёт App и не вводит App ID, installation ID, private key или webhook secret. В админке есть
одна same-origin ссылка/route `Подключить GitHub`.

Нормативный flow:

1. Аутентифицированный owner кликает `Подключить GitHub` по route `/github/app/connect`. Backend создаёт короткоживущий
   одноразовый install state, связанный одновременно с Better Auth subject и tenant, и отвечает
   `303` на `https://github.com/apps/{slug}/installations/new?state=...`.
2. На GitHub человек выбирает account или organization и доступ `All repositories` либо
   `Only select repositories`. Это единственный выбор репозиториев в сценарии.
3. Setup callback `/github/app/setup/callback` считает `installation_id` недоверенным вводом, требует ту же Better Auth
   session, валидирует и одноразово расходует неистёкший install state. Затем backend начинает
   **отдельный явный GitHub App OAuth web flow**: создаёт свежий одноразовый OAuth state и PKCE
   verifier/challenge и отправляет owner на GitHub. `request_oauth_on_install` у App выключен.
4. OAuth callback `/github/app/oauth/callback` требует ту же session, проверяет OAuth state и
   PKCE, один раз меняет `code` на временную user authorization и полностью пагинирует
   `GET /user/installations`. Указанная установка должна присутствовать в результате.
5. Backend независимо проверяет `GET /app/installations/{id}` с JWT общего App, сверяет App,
   требуемые permissions и отсутствие suspension, затем полностью получает выбранные на GitHub
   repositories без усечения пагинации.
6. Одной атомарной операцией установка уникально связывается с tenant, выпускается
   `GitHubAppConnected`, а затем `RepositoryConnected` для **каждого** выбранного на GitHub
   репозитория. Повтор завершённого callback не создаёт вторых фактов; конфликт с другим tenant
   отклоняется. После завершения временная user authorization удаляется или отзывается.

OAuth state нельзя использовать для другой session, installation или code. Если code уже был
успешно обменян, но последующая GitHub pagination или финальная транзакция оборвалась, точный
retry той же session, state и code продолжает сохранённый этап с зашифрованной временной user
authorization и не обменивает code второй раз. После завершения тот же retry только повторяет
успешный redirect и не создаёт фактов.

В приложении нет второго списка checkbox и кнопки «сохранить repositories». Изменение выбора
делается на GitHub и приходит через installation lifecycle events с последующей reconciliation.
Удаление или suspension установки останавливает новые GitHub/git операции до успешной
reconciliation. Removed repository становится неактивным в mutable installation boundary и не
получает новые task credentials; исторический `RepositoryConnected` из append-only журнала не
удаляется. Added repository становится активным и получает существующий `RepositoryConnected`,
если домен ещё не знает это подключение.

Общий App имеет permissions `administration: read`, `checks: read`, `contents: write`,
`metadata: read`, `pull_requests: write`. `administration: read` нужен для чтения branch
protection и required checks. App подписан на `pull_request`, `check_run` и installation
lifecycle/repository-selection events `installation` и `installation_repositories`.

Webhook подписывается одним deployment-scoped webhook secret. HTTP boundary сначала проверяет
`X-Hub-Signature-256` этим глобальным секретом и лишь затем использует подписанный installation
ID для tenant resolution, dedupe и domain parser. Глобальные private key, client secret и
webhook secret никогда не попадают в tenant storage, browser, journal, task или logs.

Worker не получает private key общего App. Защищённый lease-scoped control-plane protocol перед
GitHub или git фазой чеканит либо обновляет короткоживущий installation token только для task и
repository; при возможности token дополнительно сужается по repository и permissions.

## 4. Настроить модель и ключ

Два способа входа: свой API-ключ или **подписка Codex** через device-code login. Второй
сделан именно для headless: система показывает ссылку и код, человек подтверждает в браузере
у себя.

Credentials пишутся в `$CODEX_HOME/auth.json`. Файл один на `CODEX_HOME`, поэтому
`CODEX_HOME` должен быть свой на каждого тенанта.

В журнал попадает только факт подключения, никогда API key, токены или содержимое
`auth.json` — журнал вечный. `CODEX_HOME` отдельный для каждого тенанта.

OpenAI Base URL — необязательная boundary-настройка тенанта. Непустое значение нормализуется как
абсолютный HTTP(S) URL без credentials, query и fragment. Пустое значение означает официальный
endpoint OpenAI. Значение, действовавшее в due-тик, сохраняется в неизменяемом снимке задачи
`RunAgent` и передаётся Codex; последующее изменение влияет только на будущие задачи. Base URL не
является доменным фактом и не попадает в журнал.

## 5. Настроить темп и пороги

Настройки живут на двух уровнях:

| Уровень | Что настраивается |
|---|---|
| Тенант | модель и ризонинг, ключ или подписка, промпт агента, optional OpenAI Base URL |
| Репозиторий | как часто заводим, максимум открытых, через сколько закрываем |

Изменения действуют **со следующего wake-up или свипа**, задним числом ничего не
пересчитывается. Каждый доменный тик несёт использованный снимок repository settings.
Понизил порог с 12 до 5, когда открыто 9 — новые не заводятся, пока не опустится до пяти,
но уже открытые никто не трогает.

Ролей нет: у тенанта один владелец.

## 6. Понять, почему PR висит

Ради этого сценария и заводится свой экран. Он показывает цепочку:

```
что известно  →  что решили  →  почему именно  →  что дальше
```

Вердикт **пересчитывается на лету**: последний полный required inventory для текущего head
накладывается на более новые webhook-наблюдения check runs. Оборванный новый свип не стирает
последний полный снимок экрана. «Шесть часов назад было красное» бесполезно, если тест уже
починили. Цена: показанный вердикт — прогноз, а не факт.

## Доставка и восстановление наблюдений

Один `check_run` webhook может относиться к 0..N PR и превращается в столько команд, сколько
уникальных ассоциаций пришло. Поддерживаются lifecycle actions PR и `created`, `rerequested`,
`completed` для check run; остальные actions игнорируются.

Ранний check webhook может прийти без PR association или до `PrCreated`. Поэтому первый
принятый `PrCreated` обязательно создаёт эффект `ReconcilePr`: система запрашивает текущий PR
и все runs его head, не полагаясь на старую association. Повторный отчёт о том же PR второй
reconciliation не запускает.
